## 【帖文正文】

**主题：HTML 正文提取，18/31 篇抓到 0 字符——我已定位到一个反直觉的坑，但想知道你们怎么处理「不闭合标签」**

**上下文**
我在做 C1（课程资料获取与翻译），需要把 CS146S 的 31 个课程页面转成 Markdown 再送去做术语一致的翻译。用的是 Python 标准库 `html.parser`，自写提取器：遇到 `article`/`main` 进入正文态，遇到 `nav`/`footer`/`script` 进入丢弃态。

**现象**
第一版跑完，31 篇里 13 篇正常，**18 篇输出 0 字符**。更奇怪的是：用浏览器打开这 18 篇，正文明明在。

**已尝试 / 已排除**
1. 先怀疑是编码——确认 `response.content` 解码为 UTF-8 无异常，排除。
2. 再怀疑是选择器——手动 grep 了其中一个页面的 HTML，`<article>` 标签确实存在，且正文在它内部，排除「没匹配到」。
3. 打开调试日志后发现真正原因：**我打印了 `drop_depth`，发现它一旦涨上去就再也没回到 0**，也就是说丢弃态卡死了，后面所有正文全被当成「在 nav 里」丢掉了。

**具体卡点（我认为的根因）**
真实网页的 `<p>`、`<li>`、`<img>` 有大量**不闭合**的情况。`html.parser` 是流式的，它按遇到顺序回调 `handle_starttag` / `handle_endtag`，**它不会帮你补齐配对**。而我的 `drop_depth` 是一个全局整数计数器：进一个丢弃标签 +1，出一个 -1。只要页面里有个 `<div class="nav">` 欠了一个 `</div>`，这个 +1 就永远抵消不掉 → 计数器永久 > 0 → 正文全灭。

**我现在的改法**
把「深度计数器」换成**显式标签栈**：
- 进标签时把标签名压栈；
- 出标签时不是简单 -1，而是**从栈顶向上找最近的同名帧**，把它以上的全部弹出；
- 额外维护 `VOID_TAGS`（`img`/`br`/`meta`/`input`…）永不入栈，避免自闭合标签污染栈。

改完 13/31 → 28/31，字符数从 0 → 535,057。

**想请教群里的**
1. 显式栈 + 向上找同名帧，这个「自动愈合」策略在**嵌套同名标签**（比如 `<div><div>…</div>` 少一个闭合）时仍然会错，你们有没有更稳的边界规则？
2. 有人试过 `lxml.html.soupparser`（先过一遍 BeautifulSoup 的容错解析再交给 lxml）吗？在**不能装额外依赖**的场景下，标准库还有更好的写法吗？
3. 剩下 3 篇里，有 1 篇是纯图片型 PDF（无文本层），这属于「取不到」而不是「取错了」——你们在覆盖率报告里会把它算成未覆盖，还是单列「已知缺口」？

**已附证据**
- 修复前后对照：`13/31 → 28/31`，`0 → 535,057` 字符
- 最小复现（12 行，含一个故意不闭合的 `<div>`）：
  ```python
  from html.parser import HTMLParser
  class P(HTMLParser):
      def __init__(self):
          super().__init__(); self.depth = 0; self.text = []
      def handle_starttag(self, tag, attrs):
          if tag in ("nav", "footer"): self.depth += 1
          if tag == "p" and self.depth == 0: self.text.append("<p>")
      def handle_endtag(self, tag):
          if tag in ("nav", "footer"): self.depth -= 1
  html = "<nav><div>菜单<p>这是正文，但会被误杀</p></nav>"  # 少一个 </div>
  p = P(); p.feed(html); print(p.text)  # v1 输出：[]   ← 正文丢失
  ```

## 【当时的思考】（发帖前的推演，属于参与记录的一部分）

- **为什么会卡这么久**：我一开始的直觉是「提取规则写得不够全」，所以第一反应是加更多标签白名单。这是**症状驱动**的修法。真正的转折点是打印了 `drop_depth`，看到它单调不回头——才意识到问题不在「规则覆盖面」，而在「状态机本身不具备容错性」。
- **那一刻的判断**：`html.parser` 的设计契约是「忠实回调，不做修复」。把**修复职责**误加到它身上，是设计错配。要在它之上补一层「配对语义」，就得自己维护栈。
- **为什么选择栈而不是「再上一层 BeautifulSoup」**：C1 资料包要求管线可离线复用、依赖越少越好；栈方案是纯标准库、零新增依赖，且行为可解释、可打印、可单测。
- **预判群友可能的反问**：「那你为什么不直接上 `lxml.html`？」——因为 `lxml` 同样不修复错配，它只是更快；真正的修复在 `BeautifulSoup` 的 `html.parser`/`html5lib` 那一层。这个问题我准备在群里回答，作为「补充新信息」。
- **我期望的讨论走向**：从「怎么抓全」转向「**覆盖率报告要不要区分『取不到』和『取错』**」。我认为质检的价值在这里——**如果把纯图片 PDF 记成『未覆盖』，会把『资源本身没文本』误报为『我的管线有洞』**，这是会误导后续工作的假信号。
