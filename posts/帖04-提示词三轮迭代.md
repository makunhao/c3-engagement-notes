## 【帖文正文】

**主题：让 LLM 保持术语一致，靠"请准确翻译"是没用的——我迭代了三版才想清楚该把不确定性从哪里赶出去**

**上下文**
C1 要把 31 篇课程资料翻译成中文，硬要求是**同一术语在全篇译法一致**（例如 Scaffolding 一律译「脚手架」，不能一会儿「脚手架」一会儿「支撑框架」）。

**三代提示词的演化**

| 版本 | 我写的核心指令 | 结果 | 失败原因 |
|---|---|---|---|
| **v1** | "请将以下内容准确、专业地翻译为中文，保持术语一致。" | 术语一致率低，同一术语多种译法 | 「准确」「专业」「一致」都是**形容词，不是可执行的约束**。模型只能猜 |
| **v2** | 在 v1 基础上，把 84 条术语表**全文塞进** system prompt | 一致率明显上升，但**长文截断、成本高**；且模型会为了"用上术语表"而**硬塞**术语 | 把规则**当上下文**给，而不是**当约束**给 |
| **v3** | 分块 + 只注入**本块命中的术语** + 附加一段上一块译文尾部 + 明确"命中才用，未命中不许生造" | 术语违规 6 → **0**；支持断点续传 | — |

**v3 具体做了什么（可复制）**
1. **术语表按需注入**：先把该块原文与术语表做字符串匹配，**只把命中的条目**放进 prompt。避免 84 条全塞导致的注意力稀释与硬塞。
2. **加"上文窗口"**：每块附带上一块译文的**最后 500 字符**。作用是让跨块的指代（"该方法""上文提到的"）有落点。这是最容易被忽略、但对长文翻译质量影响最大的一项。
3. **给否定约束**：明确写"术语表中未列出的术语，**不要自行生造译法**，保留英文原名并在首次出现时用括号给出直译"。**加一条禁令比加十条鼓励更有效。**
4. **分块参数**：块长 3000 字符、重试 3 次、失败落盘 → 可断点续传。长任务必须可续跑，否则一次 429 就全废。

**给群里的可执行结论**
> **凡是"要有 XX 属性"式的指令，都要改写为"**可判定的**规则"。**
>
> 反面："翻译要准确、一致、专业"
> 正面："遇到术语表中 A→B 的条目必须用 B；未在表中的术语保留英文原名"

因为前者模型无法判断"我做到了没有"，后者可以直接自检。

**已附证据**
- 术语违规命中：v2 阶段抽检 6 处 → v3 修复后 **0 处**
- 三轮迭代对照表：`pipeline/prompts/翻译提示词.md`
- 参数：`MAX_CHUNK=3000, CONTEXT_TAIL=500, RETRY=3`，支持断点续传

**想请教群里的**
1. 你们用"结构化输出 + 校验"（比如让模型输出 JSON 再验证）多，还是用"分块 + 上下文窗口"多？两者在长文任务上的取舍是什么？
2. 「上一块译文尾部」这种软上下文，有人试过改成**术语使用状态追踪**（显式维护一张"已用译法表"回灌下一块）吗？效果如何？

## 【当时的思考】

- **最反直觉的一点**：v1→v2 我以为是"信息量不够"，所以猛加术语表；但真正的瓶颈是**注意力**——84 条规则对所有文本同等生效，等于没有规则。**规则的密度比规则的数量重要**。
- **另一条**：加"否定约束"是我从代码规范里迁移过来的直觉。写代码时 `lint` 报错（禁止）比 code review 建议（鼓励）有效，因为前者是**可判定的**。翻译规则同理。
- **第三点，关于可续跑**：我一开始觉得断点续传是"nice to have"。直到跑到第 19 篇时碰上 API 限流，重跑一遍 18 篇要十几分钟——**这时候才明白长任务的"可续跑"是硬需求，不是优化**。
- **准备在群里回答的**：如果有人问"为什么不直接上更贵的模型"，我的答案是——**模型换得了注意力，换不了约束的缺失**。v3 的收益主要来自 prompt 结构，不是模型档位。
