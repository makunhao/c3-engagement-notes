# 帖 02｜术语表的两份副本一定会打架：把「人读版」变成生成物

## 【帖文正文】

**主题：术语表别手写两份——`术语表.md` 应该是 `glossary.json` 的生成物，否则一致性校验等于没做**

**上下文**
C1 要把课程资料翻成中文并保证术语一致。我建了 84 条中英术语对照。一开始我做了两份：一份给人看的 `术语表.md`，一份给脚本用的 `glossary.json`。

**踩到的坑**
翻译完做一致性抽检时，脚本报出 6 处「禁用译法」，其中 3 处是**术语表本身写错了**：

| 涉及术语 | Markdown 版 | JSON 版 | 哪个对 |
|---|---|---|---|
| agent（本地运行的） | 本地代理 | 本地代理 | **都不对**——"代理"在中文语境里默认指网络代理，会误导 |
| token（服务凭证） | 服务令牌 | 服务令牌 | **都不对**——读者会以为是加密串 |
| code review | 代码审查 | 代码审查 | **都不对**——课程里同时有 design review，应作「评审」 |

也就是说：**我按 Markdown 版核对的译文，脚本按 JSON 版校验，两边标准不同 → 校验通过是假的。**

**我发现的结构性问题**
只要「人读视图」和「机器校验源」是**两个独立维护的文件**，它们就一定会漂移。这不是细心程度问题，是**结构问题**——任何一个文件被单独改了，另一份不会报错。

**我改成了什么**
把 Markdown 降级为**生成物**：

```
glossary.json  ──[generate_glossary.py]──▶  术语表.md      （人读，字段+排版）
      │
      └────────[terminology_check.py]────▶  一致性报告     （机器校验）
```

两份输出**同源**。改术语只有一个入口（改 JSON），人读版和校验规则不可能不一致。

同时我在 JSON 里加了一个 `meta.critical_terms` 字段，专门标记**高风险术语**（如 Vibe Coding=氛围编程、Scaffolding=脚手架、Context Engineering=上下文工程）。校验脚本对这批术语**一票否决**，其他术语只警告。理由是：高风险术语错一次，读者会整段理解偏。

**给群里的可执行结论**
1. 任何「术语表 / 配置表 / 字段字典」，**只保留一个机器可读源头**，人读版一律由脚本生成；
2. 校验脚本要能**反查源头**：报错时指出「是译文违规」还是「是术语表本身要改」——这两类错误处理方式完全不同；
3. 给术语**分级**（critical / normal），不要让所有术语平权——否则真正致命的错误会被淹没在噪音里。

**已附证据**
- 术语数：84 条（含 3 条 critical）
- 修复后一致性抽检：禁用译法命中数 **6 → 0**
- 脚本：`pipeline/scripts/terminology_check.py`

## 【当时的思考】

- **真正的转折**：不是「发现 6 处错」，而是发现「**我的校验脚本本身不可信**」。工具给你绿灯时，你得先确认工具有资格发绿灯。
- **一个判断**：这里有个隐蔽陷阱——两份文件都在，且都能用，**看起来更完整**（"人类友好 + 机器友好"，很专业的样子）。工程上它其实是负资产。**冗余的冗余**。
- **准备在群里补的点**：有人会说"那就写个 CI 检查两份是否一致"。我的回答是：**一致性的检查成本 > 生成的成本**。既然能生成，就不要检查同步。这是「用结构消灭问题」而不是「用纪律对抗问题」。
- **顺便自我修正**：我最初想的是"以后改文件时小心点"。这是个坏答案——**依赖人不变错的方案都是坏方案**。
